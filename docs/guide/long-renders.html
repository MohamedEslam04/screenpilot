Long renders

Render a long video without blocking your machine: stop cleanly with abort, pause and resume at a part or chunk, the memory guard, and why the output file is always playable.

A render takes about as long as the video, and longer at delivery. This page is about living with that: stopping a render, pausing it when you need the computer, and keeping a render from running the machine out of memory. How chunks and caching speed up a re-render after an edit is on the command line page.

The output is written as a partial file#

A render writes <name>.partial.mp4 and renames it to <name>.mp4 only when the video is complete. So a file with the final name is always playable, and a half-written file is never mistaken for a result. This applies to the joined video of a sequence too.

Stop a render#

Ctrl+C in the terminal, the abort tool, or cancelling the call in your AI app stops the render and everything it started: HyperFrames, Chrome and ffmpeg. They get a termination signal, and a kill after 5 seconds if they do not stop. On Windows the whole process tree is ended. The partial file is removed. Chunks and parts that already finished stay in the cache, so the next render carries on from them.

Quitting the AI app, which closes the ScreenPilot server, stops its renders too.

Pause and resume#

If you need the machine in the middle of a render (a meeting, a game), pause it instead of stopping it. The render finishes the part in progress (for a part or video of 5 minutes or more: the chunk in progress), saves where it stopped, and exits cleanly. Nothing is lost.

screenpilot pause all.json     # the sequence or storyboard being rendered
screenpilot pause              # no path: every render running now
screenpilot resume all.json    # later: carries on with the same options
  • pause drops a .pause file into the render's build folder. The render sees it at the next part or chunk boundary, writes .paused.json and stops. The render's own call (or command) then returns {paused: true, partsDone, parts, resume} and the command exits with code 0. parts lists each part as done, in progress or waiting (with chunk counts when it is chunked), and resume is the command to run.
  • resume <path> renders again with the options the render started with. Every finished part and chunk is a cache hit, so only the rest renders. You may change --workers, --min-free-mem and --mem-timeout for the rest.
  • Both take --build-dir <dir> when the build folder is not the default one.
  • A pause request that is older than the render's start is ignored, so an old .pause file cannot stop a new render.

Over MCP, the pause tool takes sequence or storyboard (or neither, to pause every render running now) and build_dir. The resume tool takes sequence or storyboard plus workers, min_free_mem and mem_timeout. Without arguments, resume keeps its older job: carrying on after someone moved the mouse while the agent drove the desktop.

A pause stops at a boundary, not instantly. A single long part with no chunks finishes completely first. Parts, or chunks inside a video of 5 minutes or more, are what give a render its pause points.

The memory guard#

Each render worker is a headless Chrome, and several can run at once. Before it starts each part or chunk, a render waits until enough memory is free. If memory does not come back in time, it fails with the measured numbers, and the finished parts and chunks stay cached.

FlagWhat it does
--min-free-mem <MB>Memory that must be available before each part or chunk. Default 1500. 0 turns the guard off. SCREENPILOT_MIN_FREE_MEM sets the default; the flag wins.
--mem-timeout <s>The longest wait for that memory, then the render fails with the numbers. Default 300.

Both flags are on render, sequence and resume; over MCP they are min_free_mem and mem_timeout. On Linux the guard reads MemAvailable; on other systems it uses what the operating system reports as free.

The result of a render has peakRssMB: the highest memory used by the render's child processes, sampled while it ran. It is useful for choosing --workers. It is not reported on Windows.
