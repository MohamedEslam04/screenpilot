The command line does the same steps as the MCP tools. Run it as screenpilot, or as node dist/cli.js from a source checkout. Most people never need it, because their AI app calls the tools for them. Use the CLI to script a render, to check a machine, or to repair a setup.

Run screenpilot --help for the list of commands and screenpilot <command> --help for the flags of one command. Commands print their result as JSON on stdout and progress messages on stderr.

The whole workflow

This block takes a recording to a finished video. Replace the paths and the voice with your own.

# 1. Record the screen. Press Enter or Ctrl+C to stop.
screenpilot record

# 2. Find idle time and clicks, and get a contact sheet image.
screenpilot analyze sessions/2026-10-27_14-02

# 3. Look closer at moments, with a 0..1 coordinate grid.
screenpilot frames sessions/2026-10-27_14-02/video.mkv --at 1,4.5,10 --grid

# 4. Write a starter storyboard (idle time cut, click zooms filled in).
screenpilot init sessions/2026-10-27_14-02 --suggest --voice ar-EG-SalmaNeural

# 5. Edit storyboard.json, then check it.
screenpilot validate sessions/2026-10-27_14-02/storyboard.json

# 6. Render a fast draft and look at frames of the result.
screenpilot render sessions/2026-10-27_14-02/storyboard.json -q draft
screenpilot check sessions/2026-10-27_14-02/storyboard.mp4 --at 2,8,15

# 7. Render the final video.
screenpilot render sessions/2026-10-27_14-02/storyboard.json -q delivery -o demo.mp4
Times in a storyboard and in frames --at are source seconds (the raw recording). Only check --at uses output seconds (the rendered video). See the storyboard reference.

Update

update

screenpilot update replaces the app files (dist, skill, python and the version files) with the latest release, a few MB instead of the whole package. It checks the SHA-256 of the download, keeps the old files in .update-backup, and puts them back if a step fails. It never touches Node, ffmpeg, node_modules or your AI app settings. When a release changes those, or when you run from a developer checkout, it refuses and says why. Install shows the steps for each system.

FlagWhat it does
--checkOnly say whether a newer version exists, and print the command to run. Changes nothing.
--source <folder|url>Read latest.json and the archive from a folder or an address instead of GitHub Releases (offline machines, tests).

Decisions first

brief

screenpilot brief prints the decisions an AI app must ask you before it records or builds anything, with the options available on this computer. It also prints recommendedSetup: what the recommendations are based on (the existing video in the folder, then your usual choices) and one line per decision, so the app can offer it as a single question. --project <path> points it at another folder or storyboard.json; the content question is optional. It is for AI apps that use the CLI; with MCP the brief tool asks you directly. See Tools.

screenpilot validate <storyboard> checks the file against the schema and the source video. It fails with the list of schema issues, or prints valid: true with warnings such as overlapping segments, items past the end of the video and callouts without x and y.

screenpilot schema prints the storyboard JSON Schema. It is the authority on every field.

screenpilot voice-setup [voicetut|namaa] installs a local voice model. The default is voicetut. It needs uv, which also fetches Python 3.11. Render and check

render

screenpilot render <storyboard> makes the voice, cuts the video and renders an MP4. It takes minutes. It prints the output path, the duration, the freezes it added (autoHolds), the narration lines that need a speed-up to fit (fit), the timeline file and warnings. When a narration line is longer than its slot, the render freezes the video so lines never overlap. The video is written as <name>.partial.mp4 and renamed when it is complete, and <name>.timeline.json is written next to it (see Subtitles and timeline).

--png-framesUse lossless source frames: sharper text in the recorded UI, slower.
--workers <n>Parallel renderers, each a headless Chrome: auto (default: half your CPU cores, limited by free memory, 1 to 6), max (all cores but two, limited by free memory) or a number. max is faster but makes the desktop sluggish, so use it when you are away. --formats <list>Render once per format, for example 16:9,9:16,1:1. See Several formats.

--subtitle-chars <n>Characters per caption line for --subtitle-lang. Default 42, at most 2 lines per caption.

--build-dir <dir>Where the HyperFrames project is written. Not allowed with --formats.

Partial renders

To review one stretch of a long video, render only that window with --from and --to. Both are output seconds, the same seconds check uses: look at the draft, find the problem at 12 to 20 seconds, fix it, and render just that window again. You can give only --from (to the end) or only --to (from the start).

screenpilot render storyboard.json -q draft --from 12 --to 20

The file is <storyboard>.part-12-20.mp4 (part-12-end when you give no --to), built in <storyboard>.part-12-20.build. It is a short render of just that window, so it is much faster than the whole video. Items outside the window are left out, and the music level, including ducking, carries into it.

Several formats

--formats renders the same storyboard once per output size, so one edit gives you a YouTube cut, a Reels cut and a feed cut. The voice is generated once for all of them.

screenpilot render storyboard.json --formats 16:9,9:16,1:1 -o demo
FormatSizeFile
16:91920x1080<name>.16x9.mp4
9:161080x1920<name>.9x16.mp4
1:11080x1080<name>.1x1.mp4
WxH, for example 1280x720as given<name>.1280x720.mp4
  • Width and height must be even. Duplicate formats are dropped.
  • -o becomes the base name: -o demo writes demo.16x9.mp4 and so on. Without -o, the base is the storyboard name.
  • --build-dir cannot be combined with --formats. Each format has its own <name>.<format>.build folder.
  • --from and --to work together with --formats: the files become <name>.9x16.part-12-20.mp4.
A portrait or square export of a landscape recording crops the picture. Views that frame a window fill the frame, so the long side of the window is trimmed. Monitor views still show the whole monitor. Look at a 9:16 draft before you deliver it.

Subtitle files and extra outputs

Platforms that take a caption file (YouTube, LinkedIn, Vimeo) want the words as a file, not burned into the picture. --subtitles writes them from the narration, in the video's own timing, next to the MP4. Every narration line is included, even one you hid from the picture with "caption": false.

screenpilot render storyboard.json -q delivery -o demo.mp4 --subtitles srt,vtt --also gif,poster
OptionFileNotes
--subtitles srtdemo.srtSubRip, the most widely accepted.
--subtitles vttdemo.vttWebVTT, for the web.
--also gifdemo.gifAnimated GIF, 800 px wide at 12 frames a second, no sound. It gets big fast: use it for a short clip, a README or a chat.
--also webmdemo.webmVP9 video with Opus sound. Smaller than the MP4 for the web.
--also posterdemo.poster.pngOne frame at full size, for a thumbnail or the poster of a video tag. Set the time with --poster-at.

The files are listed under files in the result. They follow --from/--to (a partial render writes the subtitles of that window) and --formats (one set per format).

For several languages, for a video that is already rendered, and for soft subtitle tracks, see Subtitles and timeline and subs.

Long renders

A full render takes about as long as the video, and longer at delivery. Each finished render of 5 seconds or more is timed (render-speed.json in the cache folder). When the next render is expected to take 2 minutes or more, the log starts with estimated ~<time>, worked out from your last renders at that quality. It is never printed when there is no history yet.

  • Iterate on a draft window. Use -q draft with --from and --to, and keep -q delivery for the final file.
  • Use all the cores when you are away. --workers max (or SCREENPILOT_WORKERS=max) uses all cores but two. The default is half the cores so the desktop stays responsive.
  • Chunks start at 5 minutes. A video (or a --from/--to window) of 5 minutes or more renders automatically in chunks of about 3 minutes. A chunk is cut only where nothing is in progress: no narration line, caption, card, hold, transition, camera move, overlay video or music fade crosses the cut. When there is no such point, the video renders in one piece.

Each chunk is cached in <name>.build/chunks/<quality>/, keyed by its own content in chunk-relative time. After an edit, only the chunks it touched render again. The log says chunk 3/12 (...): unchanged, reusing for the others. Then the chunks are joined (the video is copied, the audio is encoded once), and loudness, subtitles and --also run once on the joined file.

  • An edit that moves everything after it by whole seconds (a 2 second hold, a card) keeps the later chunks. A fractional shift, which is what most narration-length changes cause, renders them again.
  • A failed chunk names its output range. Run the render again and it resumes from the chunks that finished.
  • --no-chunks renders in one piece. --chunk-seconds <n> sets the chunk length.
  • Stopping is safe. Ctrl+C (or the abort tool) stops the render with its whole process tree, and the video is written as <name>.partial.mp4 and renamed only when complete, so a file with the final name is always playable.
  • Pause when you need the machine. pause stops after the part or chunk in progress and resume carries on from the cache.

The Long renders page has the details of pausing, resuming and the memory guard.

Chunks speed up the render after a small edit, not the first render. To combine different recordings, a sequence of parts is still the way.

History of your work

ScreenPilot keeps a list of what it recorded and rendered. It is one JSON line per finished job in history.jsonl, in the config folder. Recording (record), performing a take (perform), render and sequence add a line when they end. A failed render or sequence is recorded too, with its error. The parts of a sequence and the render during setup add nothing, so each video appears once.

history

screenpilot history prints the newest events first, as a JSON list.

FlagWhat it does
--limit <n>How many events. Default 50.
--before <iso>Only events older than this time. Pass the at of the last event of the previous page to get the next page.
--liveList the renders running now instead of the history.

Each event has these fields. Fields that do not apply are left out.

FieldMeaning
vFormat version, always 1.
atISO time the work finished.
kindrecord, take, render or sequence.
statusok or failed.
pathThe session folder (record, take), the storyboard (render) or the sequence file (sequence).
storyboardThe storyboard a take wrote (take only).
outputThe video it made or recorded.
durationSecLength of that video in seconds.
qualityRender quality (render, sequence).
wallSecondsHow long the work took.
errorThe error message of a failed job, cut to 500 characters.
importedtrue when library import found it on disk.

With --live, each running render or sequence has one small file in the jobs folder of the cache folder. The file is removed when the job ends. A file left by a process that crashed is removed the next time you list. A job has id, pid, kind, path, quality, startedAt, updatedAt, and step (label, index, total) when it knows its progress, such as chunk 3 of 12 or part 2 of 4.

screenpilot history --limit 10
screenpilot history --live
Writing the history never makes a job fail. If the file cannot be written, the job still finishes and the line is skipped.

library

screenpilot library import adds work you made before the history existed: recordings (a folder with meta.json) and finished renders (a storyboard.json with storyboard.mp4 next to it). It looks two folder levels deep under each root. What is already in the history is left alone, and added lines are marked imported. It prints how many it added and how many events the history now holds.

FlagWhat it does
--root <dir...>Folders to look in. Default: the sessions folder (SCREENPILOT_OUTPUT, else ./sessions).
 
screenpilot library import --root ~/Videos/ScreenPilot
The import rewrites history.jsonl in time order. Run it when no render is about to finish.

Set up and check this machine

setup

screenpilot setup copies the app to its folder, adds ScreenPilot to every AI app it finds, and prepares the render browser. Restart the AI app afterwards. Config files are backed up before they change.

FlagWhat it does
--listList the AI apps setup knows and whether each is installed here.
--clients <ids>Only these client ids, for example claude-desktop,claude-code,codex,opencode,cursor.
--removeRemove ScreenPilot from those apps instead.
--output <dir>Where videos are saved. Default ~/Videos/ScreenPilot.
--in-placeRegister the package where it is, without copying it.
--skip-prepareDo not download the render browser or run the test render.
--allow-toolsClaude Code only: let the agent use every ScreenPilot tool without asking each time. It adds a rule to ~/.claude/settings.json.
--printOnly print the config to paste into an AI app by hand.

doctor

screenpilot doctor checks this machine: ffmpeg, desktop, monitors, OBS, the demo browser and voices, including an "accessibility tree" check, a "local voice" check that is skipped when you have not set up a local voice (it is optional), and "elevenlabs voice" and "gemini voice" checks that only say whether a key is set (also skipped when it is not; no request is made). It prints a JSON report and a one-line summary. The exit code is always 0, so read the report. Add --input to also test input injection; this moves the real pointer for a moment.

Run screenpilot doctor first on a new machine, and again whenever recording or driving fails.
