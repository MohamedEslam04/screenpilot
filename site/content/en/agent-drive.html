Instead of asking you to perform the demo, the agent can do it. It looks at your screen, moves the real mouse, clicks, types and scrolls, and ScreenPilot records everything while it does. The result is a recording plus a starter storyboard.json that goes into the normal edit and render loop.

This page is for developers and for anyone who wants to read or edit the file the agent writes. The file is called a take: take.json.

The agent uses your real mouse and keyboard. Keep your hands off the mouse while it runs: moving the pointer stops the action. Read Safety before you let an agent run unattended.

The loop

Every driven demo follows five steps. The agent runs them; you can also run them yourself from the command line.

  1. Explore. Look before you act: screenshot (with a 0..1 grid), windows, browser_open for web apps. Act with click, type_text and the other drive tools, and take a new screenshot after each action to check it worked.
  2. Write take.json. Read the schema first: take_schema (MCP) or screenpilot take-schema.
  3. Rehearse. Run perform with dryRun (CLI: screenpilot perform take.json --dry-run). It drives the desktop with the same actions but does not record. When a step fails, the error names the step. Fix it and run again until it is clean.
  4. Perform. Run perform without dryRun. ScreenPilot records, drives, and writes a session folder with the video, events.jsonl and a starter storyboard.json.
  5. Review and render. Look at the result with analyze and get_frames, edit the storyboard, validate it, render a draft, check it, then render the delivery quality. See Storyboard reference.
A dry run still makes the voice clips for your say lines, so the first one needs internet. The clips are cached next to the take, so later runs reuse them.

Commands

screenpilot screenshot [--screen eDP-1] [--grid]   # what each monitor shows
screenpilot windows                                # open windows and their geometry
screenpilot browser --screen HDMI-A-1 --url https://example.com
screenpilot drive move eDP-1,0.5,0.5               # also: drive click, type, key, scroll
screenpilot a11y tree --app gedit                  # controls of a native app (role, name, rect)
screenpilot take-schema                            # print the take.json schema
screenpilot perform take.json --dry-run            # rehearse: same actions, no recording
screenpilot perform take.json                      # record and drive; writes the session folder

In an AI app, the same steps are MCP tools. See Tools for the full list.

What a take looks like

A take is one JSON file. Only steps is required.

KeyDefaultWhat it does
namenoneA label for you.
screens"all"Which monitors to record: "all" or a list of monitor names.
voiceen-US-AndrewNeural, rate +0%, gap 0.35The voice for say lines (name, rate, gap in seconds between lines).
setup[]Steps that run before the recording starts: open apps, place windows. Use it for browser, open, run, focus and waitForWindow.
stepsrequiredThe demo itself, at least one step.
tail1Seconds to keep recording after the last step or voice line.
camera"window"How the starter storyboard frames the video: "window" follows the app in use, "screen" follows the monitor, "all" shows every monitor side by side. view steps always win.

Paths in a take (a browser URL or goto given as a file) are relative to the take file. Write site/index.html, not an absolute path from your machine.

Targets

Steps that point at something (click, move, drag, scroll) take a target. There are four forms.

FormMeansUse it when
{ "web": "selector" }An element in the demo browser, found by a Playwright selector: CSS, text=Submit, role=button.The demo is a web app. This is the exact, preferred form: it finds the element wherever it is on screen.
{ "a11y": { "role": "button", "name": "Save" } }A control in a native app, found through the accessibility tree. It resolves to the control's centre. See Native apps.A native app with named controls (buttons, menus, fields). It finds the control even when the layout or window position changes.
{ "window": "match", "x": 0.5, "y": 0.5 }A point inside the first window whose class or title contains match. x and y are 0..1 inside that window.A native app, when the desktop can list windows. The point stays right even if the window moves.
{ "screen": "eDP-1", "x": 0.5, "y": 0.5 }A point on one monitor, 0..1 (x from the left, y from the top). Without screen it is the monitor under the pointer.Everywhere. It is the only form that works on desktops with no window control (GNOME on Wayland).
To read screen coordinates, take a screenshot with grid on and read x and y off the grid. To check that a {web} target exists before you click, call web_locate. For an {a11y} target, call a11y_find.

Native apps: {a11y} targets

An {a11y} target finds a control by its role and name through the operating system's accessibility tree, then resolves to the centre of that control. It only locates. The real pointer still moves there and clicks, so the recording shows a normal cursor. It works wherever a target is accepted: click, move, drag, scroll (at) and waitFor.

KeyWhat it does
roleThe control type: button, checkbox, radio, tab, textbox, menuitem, combobox, listitem and similar, or an AT-SPI name such as push button, menu item, entry.
nameThe control's label. It matches when the name contains this text, ignoring case.
appThe app to look in: its window class or title contains this text. Without it, ScreenPilot looks in the app of the focused window when the desktop can tell, and in every app otherwise.
exacttrue matches the whole name, not a part of it.
nth1-based pick when several controls match.

Give a role or a name, or both. If several controls match, the step fails with a list of candidates. ScreenPilot never guesses: add nth or a more specific name.

{ "click": { "a11y": { "role": "button", "name": "Save", "app": "gedit" } } },
{ "waitFor": { "a11y": { "role": "menuitem", "name": "Open" }, "timeout": 10 } }

Read the app first. a11y_tree lists the controls with role, name, states and a rectangle, and a11y_find checks that a target matches exactly one control. From the command line: screenpilot a11y tree [--app X] [--all], screenpilot a11y find <role>:<name> [--app X] [--exact] and screenpilot drive click a11y:<role>:<name>.

Where it works

  • Linux, KDE Wayland: works, through AT-SPI (tested on KDE Plasma).
  • Linux, X11: works the same way (tested on a nested X server without a window manager; not yet on a full X11 desktop).
  • GNOME and other Wayland desktops: the desktop does not tell where a window is. The tree can be read (a11y_tree), but a click fails with POSITION_UNKNOWN. Use {screen, x, y} targets there.
  • macOS: built on the Accessibility API and tested on a real macOS runner in CI. The AI app needs the Accessibility permission.
  • Windows: built on UI Automation, read by a short PowerShell script (nothing to install) and tested on a real Windows runner in CI. Apps that expose their controls to UI Automation only as plain panes (the text area of the classic Notepad, for example) show no control there: use {window, x, y} or {screen, x, y} targets for those. An app running as administrator cannot be read unless the AI app runs as administrator too.
Qt apps only appear in the accessibility tree if they were started with QT_LINUX_ACCESSIBILITY_ALWAYS_ON=1. Apps that a take starts with run or open get it automatically. A Qt app that is already running must be restarted. Apps that draw their own interface (some Electron and GPU-drawn apps) show little or nothing. Chromium needs --force-renderer-accessibility; in the demo browser use {web} targets instead.

Target errors

When a target cannot be resolved, no input was sent, so trying again is safe. The error carries a code and says so: delivery: "not_delivered" and retry: "safe".

CodeMeaning
ELEMENT_NOT_FOUNDNo control matches. Read the app with a11y_tree.
AMBIGUOUS_TARGETSeveral controls match. The error lists them. Add nth or a more specific name.
TARGET_COVEREDA {web} element is on the page but something (a sticky header, a clipping box) covers its centre, so a click would hit the wrong thing. Scroll it clear or close what covers it. A click step with force: true skips the check. Other windows are not detected.
APP_NOT_FOUNDNo accessible app matches. Is it running? For Qt apps, see the warning above.
WINDOW_NOT_FOUNDNo window matches a {window} target or a focus step. The error lists the windows that exist.
A11Y_UNAVAILABLEThe accessibility source of this desktop could not be read (for example no accessibility bus on Linux, or PowerShell missing on Windows).
POSITION_UNKNOWNThe control was found but the desktop does not say where the window is.
TIMEOUTA waitFor did not see the control in time.

MCP tool errors end with a JSON line {code, delivery, retry}. A failed perform returns the same fields, plus candidates when there are any, next to failedStep. When several windows match a {window} target or focus, the focused one is preferred.

Every step

Each step is an object with one main key. Unknown keys are rejected, so a typo fails validation instead of being ignored.

StepOptionsWhat it does
sayvoice, waitA narration line at this moment. A line never starts before the previous one ends. With wait: true the take pauses until the line finishes.
captiondur (3), position (bottom, top, center)Show a short text on screen for dur seconds.
viewPoint the camera at a monitor name, or "all" for every monitor. Without view steps the camera follows the pointer.
browserid (main), screen, url, appOpen the demo browser on a monitor. app: true hides the address bar and tabs, so the video shows only the page. Another id opens a second demo browser. See Two demo browsers.
tilebrowsers, screenPlace demo browser windows side by side, left to right in the order of browsers, inside the monitor's usable area.
gotoSend the demo browser to a URL or a file path.
movedurMove the pointer to a target, like a hand would.
clickbutton (left, right, middle), count (1 to 3)Move to a target and click. count: 2 is a double click.
dragdurPress at from, move to to, release. Both are targets.
typecpsType text into the focused field at human speed. cps is characters per second. Give a string, or { "env": "NAME" } for a secret.
keyPress a combo such as ctrl+l, enter or alt+tab. On macOS use cmd+l, not ctrl+l.
scrollat, horizontalScroll by whole steps. Positive goes down (or right with horizontal), negative goes up. at is a target to move to first.
waitPause for a number of seconds.
waitForweb or a11y, timeout (30)Wait until an element shows up in the demo browser (web) or a control shows up in a native app (a11y). Fails if it does not appear in time.
waitForWindowmatch, timeout (15)Wait until a window whose class or title contains match exists.
focusmatch or browser, screenRaise a window, and optionally move it onto a monitor. browser (true for the main demo browser, or an id) finds a demo browser by its process, not by its title.
openOpen a file or URL with the system default app.
runStart a program from a list: ["xdg-open", "~/Downloads/x.pdf"]. There is no shell, so no pipes or quotes. Prefer open. Apps started by run and open get QT_LINUX_ACCESSIBILITY_ALWAYS_ON=1, so Qt apps show up for {a11y} targets.

say, caption and view do not touch the desktop. They are written into the starter storyboard as narration, captions and camera switches, at the moment they happen. Inside setup they do nothing.

Two demo browsers

To show an admin and a user at the same time, for example to show a live effect, open a second demo browser. A step { "browser": { "id": "user", "url": "https://app.example.com" } } opens it with its own profile (browser-user in the config folder) and its own debugging port. The main browser uses port 9333, and the others get 9334, 9335 and so on, in the order they are first used.

  • Pick a browser per step. Every {web} target, waitFor.web, goto and highlight takes "browser": "user". The default is "main".
  • Focus it. { "focus": { "browser": "user" } } brings that browser to the front.
  • The camera. With two or more browsers the generated storyboard gets one view of the tiled area (or around the windows when nothing was tiled) instead of views that follow windows. A take with its own view steps or camera: "all" keeps them. Highlights map from the browser they were measured in.

Tile the windows

{ "tile": { "browsers": ["main", "user"], "screen": "eDP-1" } } places the browsers side by side. screen is optional: the default is the monitor of the first browser. The windows get equal widths, left to right in list order (also for right-to-left apps).

The windows use the full height of the monitor's usable area: below a top panel, above a taskbar or dock, and beside a side panel. Where the desktop cannot report that area (for example GNOME or wlroots Wayland), the whole monitor is used.

Try it live over MCP

Explore the second browser before you write the take. browser_open takes the same id (an id that is already open is reused and navigated, never started twice). Then pass the same id as browser to web_locate, wait_for (its web form) and page_text. A second browser that is not open yet fails with "Call browser_open with id ... first". Ports and profiles come from the same registry perform uses, so you can try the second browser live and then write the take with the same ids.

A complete take

This take fills in a web form, downloads a file, opens it in a native app on the laptop screen, and scrolls it. The last voice line overrides the voice. The monitor names (HDMI-A-1, eDP-1) are examples: use the names that screenshot or doctor report on your machine.

{

  "voice": { "name": "en-US-AndrewNeural", "rate": "+0%" },

  "steps": [

    { "say": "Let's open a support ticket.", "wait": true },
    { "wait": 0.6 },
    { "click": { "web": "input[name=subject]" } },
    { "type": "Cannot export my report" },
    { "click": { "web": "textarea[name=body]" } },
    { "type": "The export button spins forever on large reports." },
    { "caption": "Describe the problem", "dur": 3, "position": "top" },
    { "say": "Then we send it.", "wait": true },
    { "click": { "web": "text=Submit" } },
    { "waitFor": { "web": "text=Download receipt", "timeout": 20 } },
    { "click": { "web": "text=Download receipt" } },

What perform gives you

A performed take produces a session folder with the video, events.jsonl (the clicks come from what the driver did, so they are exact) and a storyboard.json. The storyboard already has zooms placed on the clicks, your narration and captions at the right times, and the camera views. Each type step is also marked as a typing span (a secret from an environment variable is timed, never copied), so sounds.typing can play on it. Edit it like any storyboard.

From the CLI the folder is sessions/<timestamp> unless you pass --dir. From an AI app it is a new folder in the ScreenPilot folder inside your Videos folder (Movies on a Mac), or in the video folder of the project the app is working in when that project has a .screenpilot.json (see the FAQ).

When a step fails, the take stops, keeps whatever was recorded so far, and reports which step failed. In an AI app the result has failedStep, error and partial, plus code, delivery, retry and candidates when the step failed on a target (see Target errors). Look at the partial recording to see where it went wrong.

Tips

  • Say it, then click. Put a say with wait: true before an important click so the viewer hears what is about to happen first.
  • Wait for things, not for time. After a click that loads something, use waitFor or waitForWindow instead of a long wait. Keep plain waits to 0.3 to 1 second after a page change.
  • Keep takes short. Stay under about 90 seconds. A shorter take is faster to rehearse and easier to edit.
  • Keep lines short. One sentence, under about 12 words. The render freezes the video when a line is longer than its slot, so long lines add dead time.
  • Prefer {web} targets inside the demo browser. They find the element, so they do not break when the layout changes. In a native app, prefer {a11y} over screen coordinates, and check it with a11y_find first.
  • Secrets go in the environment. Use { "type": { "env": "NAME" } }. The value is read from the environment when the step runs and is never logged or printed. Never write a password into take.json.
  • Always rehearse. A dry run costs seconds. A failed real take costs a recording.
  • Show nothing private. Open pages with "app": true so no address bar, tabs or local paths appear.

What each desktop supports

Driving works on KDE Plasma, any X11 desktop, GNOME on Wayland, Windows and macOS. It does not work on sway or Hyprland, where recording still works.

  • KDE Plasma, X11 desktops, Windows, macOS: everything in this page works, including {web} and {window} targets, focus and waitForWindow. {a11y} targets are tested on KDE Plasma and on X11 (nested X server), on macOS and on Windows (both tested on a real runner in CI; see above for the Windows limit).
  • GNOME on Wayland: no window control. Use only { "screen", "x", "y" } targets. The focus and waitForWindow steps and the {window} and {web} targets fail with an error. {a11y} controls can be read but not clicked.
  • sway, Hyprland: driving is not possible.

On Wayland, the first drive asks you to approve a remote control dialog once. On macOS the AI app needs Accessibility permission. On Windows, apps that run as administrator cannot be driven unless the AI app runs as administrator too. See Platforms for the full table.
